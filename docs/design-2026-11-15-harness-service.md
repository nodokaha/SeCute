# 設計メモ: ハーネスのサービス化と API トークン管理（2026-11-15）

## 背景と現状

- ハーネスは CLI（`seccheck.py run --target … --profile …`）であり、実行は
  スキル経由でエージェントまたは人が起動する形式。呼び出し側はリポジトリの
  配置とツールの知識を必要とする。
- トラッカーは FastAPI のサービスで、書き込み API は `SECUTE_API_TOKEN`
  （環境変数の固定値1個、`X-API-Token` ヘッダー）で保護される。
  未設定時は起動しない fail-closed 仕様。
- 取り込みの実行履歴は `ingest_runs` に残るが、ハーネスの実行履歴を
  管理する仕組みはない。`report.json`（schema_version 2）はファイルとして
  生成され、サービス側へは手作業で渡される。

## ゴール

1. ハーネスのチェック実行を API で依頼できるようにする。呼び出し側は
   リポジトリのクローンもツールの知識も持たず、トークンと API だけで
   実行・結果取得ができる（CI、スクリプト、AI エージェント等を想定）。
2. API トークンを連携画面（ダッシュボード）から発行・失効できるように
   する。名前とスコープを持ち、保存はハッシュのみ。
3. 対象とプロファイルを登録しておけば、定期実行と Webhook で自動的に
   チェックが回り、結果がトラッカーに蓄積される。

## 非ゴール

- サンドボックス隔離方式の変更（cap-drop ALL、no-new-privileges、
  seccomp、非 root、tmpfs 上限、ネットワーク既定 none は現行維持）。
- チェック内容（プロファイル、ツール、正規化ルール）の変更。
- マルチユーザー対応。トークンは「呼び出し元」の単位であり、利用者
  アカウント体系は導入しない。

## 全体構成

- **コントロールプレーン**: トラッカーに実行 API とトークン管理を追加。
- **ランナー**: 既存の `seccheck.py run` をサブプロセスとして起動し、
  ジョブの状態遷移と `report.json` の取り込みを担う。当面はトラッカーと
  同一ホストで動かし、将来の分離に備えて内部インターフェースを分ける。
- **スケジューラ**: 定期実行の起票と Webhook の受付を行い、実行 API と
  同じ経路でジョブを投入する（自動実行も通常のジョブとして記録する）。

## 実行 API

| メソッドとパス | 内容 | 必要スコープ |
|---|---|---|
| `POST /api/runs` | 実行依頼。body: `target`, `profile`, `network`, `timeout`。`202` で `job_id` を返す | `runs:write` |
| `GET /api/runs` | 実行履歴の一覧（新しい順） | `runs:read` |
| `GET /api/runs/{id}` | 状態とサマリ（全体ステータス、チェック別ステータス、件数） | `runs:read` |
| `GET /api/runs/{id}/report` | `report.json` 全文 | `runs:read` |
| `POST /api/runs/{id}/cancel` | 実行中ジョブの中止 | `runs:write` |

- ジョブの状態: `queued → running → complete | partial | failed`
  （末端状態は report の全体ステータスと語彙を揃える）。
- 実行履歴は新テーブル `scan_runs` に記録する（`ingest_runs` と対の関係）。
  列: `id, target, profile, status, token_id, trigger
  (api | schedule | webhook), started_at, finished_at, report_path,
  error`。
- 同一ターゲットの同時実行は1つまで。それ以外はキューで待つ。
- タイムアウト時は既存方針どおり未完了として記録し、部分出力は成功と
  みなさない。

## API トークン管理

新テーブル `api_tokens`:

| 列 | 内容 |
|---|---|
| `id` | 主キー |
| `name` | 呼び出し元の識別名（例: ci, agent） |
| `token_hash` | トークンの SHA-256 ハッシュ。平文は保存しない |
| `scopes` | カンマ区切りのスコープ一覧 |
| `created_at` / `last_used_at` / `revoked_at` | 発行・最終利用・失効の時刻 |

- スコープ: `runs:read`, `runs:write`, `ingest:write`, `items:write`,
  `admin`（トークン管理自体）。
- 連携画面（ダッシュボード配下）:
  - トークンの発行（名前とスコープを選択 → 平文は発行時に一度だけ表示）
  - 一覧表示（名前、スコープ、最終利用、状態）
  - 失効（即時反映）
- 認証は既存の `X-API-Token` ヘッダーを踏襲し、エンドポイントごとに
  スコープを検証する。
- 環境変数 `SECUTE_API_TOKEN` はブートストラップ用として残す
  （`admin` 相当、トークン未発行でも画面に入れるための初期経路）。
  将来的に画面発行トークンへ一本化するかは未決。
- 実行・取り込みの記録には `token_id` を残し、誰が回したかを
  provenance として追えるようにする。

## 自動実行

- **定期実行**: `schedules` テーブル（`target`, `profile`, 実行間隔、
  `enabled`）をスケジューラが巡回し、間隔を過ぎたものを起票する。
- **Webhook**: `POST /api/hooks/{hook_id}`。フックごとに秘密値を発行し、
  `X-Signature` の HMAC-SHA256 で検証する。ペイロードから対象を特定する
  変換はフック側の設定に持たせ、任意コード実行はさせない。
- 自動実行の結果は通常のジョブと同じく `scan_runs` に残り、失敗時は
  次回間隔まで再試行しない（連続リトライで対象を叩かない）。

## セキュリティ上の注意

- トークン平文は発行時表示と呼び出し側の保持のみ。ログに出力しない。
- Webhook の署名検証に失敗したリクエストは起票しない。
- ランナーは既存サンドボックス内でのみ対象を実行する。API から渡される
  `target` の解釈（パス／URL の許可範囲）はランナー側で検証し、
  ホスト上の任意コマンド実行に繋げない。
- 連携画面は既存のアクセス制御（リバースプロキシ側の認証）の内側に
  置く前提とし、画面自体の操作にも `admin` スコープのトークンを要求する。

## 段階導入

- **Phase A**: `scan_runs` と実行 API。認証は既存の環境変数トークン。
- **Phase B**: `api_tokens` と連携画面、スコープ検証。環境変数トークンは
  ブートストラップに降格。
- **Phase C**: `schedules` と Webhook による自動実行。

## 未決事項

- ランナーの配置（トラッカーと同一プロセス／別コンテナ）と同時実行数。
- `report.json` の保持期間と、古いレポートの削除方針。
- トークン失効時、その呼び出し元が投入した実行中ジョブを止めるか。
- 環境変数トークンを完全に廃止するか、緊急用として残すか。
