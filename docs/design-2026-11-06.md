# セキュリティチェック・サンドボックス＆脆弱性トラッカー 設計案

作成：2026-11-06（清涼の「考案」依頼）
プロジェクトのリポジトリ：https://github.com/nodokaha/SeCute（2026-11-06に清涼が作成、作成時点では空）
前提の環境：セルフホスト群（Coolify／Docker／Cloudflare、Karakeep、Outline、Basisサーバ群）、GitHub の自作リポジトリ（Basis-AccountServ 等）、音楽配信用 PC（Guix System）、Unity クライアント。毎朝のセキュリティニュース配信（8:47）とは連携させる。

## A. セキュリティチェック・サンドボックス「ハーネス」

### 目的
「チェックしたい対象（リポジトリ／コンテナイメージ／自前 Web アプリ）を、本番や自宅 LAN に触れさせずに、使い捨ての隔離環境で安全に検査し、結果だけを持ち帰る」ための実行基盤。検査する側もされる側も信用しない設計にする。

### 全体像
- **ランナー**：ジョブごとに使い捨てコンテナ（Docker）を1つ起動し、終わったら破棄する。対象コードは読み取り専用マウント。ホストの Docker ソケットは渡さない。
- **ネットワーク**：既定で外部通信は遮断し、許可リスト（パッケージレジストリ、NVD／OSV 等の脆弱性 DB、対象の取得元）だけ通す。本番サービスや自宅 LAN への到達性は持たせない。
- **資格情報**：本番の秘密情報は一切渡さない。必要な場合も読み取り専用・最小権限の使い捨てトークンだけ。
- **制限**：実行時間・CPU・メモリに上限。タイムアウトしたら結果なしで破棄。
- **成果物**：正規化した JSON レポート（チェック種別・重要度・該当箇所・根拠）＋人間向け要約。前回との差分（新規検出だけ）を出せるように履歴を残す。

### チェックのプラグイン構成（最初の候補）
| 種別 | ツール候補 | 対象 |
|---|---|---|
| 依存関係の脆弱性 | OSV-Scanner / Trivy | リポジトリ、イメージ |
| シークレット混入 | gitleaks | リポジトリ（履歴含む） |
| コンテナ／設定 | Trivy config / Hadolint | Dockerfile、compose、イメージ |
| 静的解析 | Semgrep | 自作コード（Basis サーバ、AccountServ） |
| Web の外形 | testssl.sh / ヘッダ確認スクリプト | Karakeep、Outline 等の公開面 |

### 使い方のイメージ
```
seccheck run --target github:nodokaha/Basis-AccountServ --profile repo
seccheck run --target image:basis-server:latest --profile image
seccheck run --target https://karakeep.example.com --profile web
```
- プロファイルで「どのチェックを束ねるか」を決める。追加はプラグインを足すだけ。
- 実行は手動＋夜間の定期実行（cron）。定期実行は「前回から増えた検出」だけを通知する。

### 安全側の要点（ここが本体）
- 対象コードは「実行されるかもしれないもの」として扱い、ビルドやテストの実行もサンドボックス内だけに閉じる。
- スキャナ自体もサンドボックス内で動かす（スキャナの脆弱性や誤作動をホストに持ち込まない）。
- レポート以外の書き込み口を持たせない（結果 JSON の出力専用ボリュームのみ書き込み可）。

## B. 脆弱性トラッカーサイト

### 目的
「世の中の脆弱性情報」ではなく「**自分の環境に関係する脆弱性だけ**」を追う個人用サイト。毎朝のニュース配信はその先頭部分の要約、という位置づけにする。

### データの取り込み（ソース）
- CISA KEV（悪用確認済みカタログ）
- JPCERT/CC・IPA の注意喚起
- GitHub Advisory Database / OSV.dev（依存関係と突き合わせやすい）
- NVD（CVE の詳細・CVSS）
- 取り込みは1日数回のポーリング。ソースごとに「取得日時」を必ず保持し、古い情報を新しいものとして見せない。

### 資産インベントリ（突き合わせの要）
自分の環境を「製品＋バージョン」で登録しておく。初期登録の候補：
- Coolify、Docker、Cloudflare Tunnel（cloudflared）
- Karakeep、Outline
- Basis サーバ（依存ライブラリ含む）、Basis-AccountServ
- Unity（クライアント開発環境）
- Guix System（音楽配信用 PC）の主要パッケージ
- OpenSSH、Linux カーネルなど基盤系

### 突き合わせと状態管理
- 取り込んだ CVE を製品・バージョン範囲でインベントリと照合し、「要対応／様子見／対象外」を自動で一次判定する（最終判断は人間）。
- 各項目に状態を持たせる：未確認 → 対応中 → パッチ済み／緩和済み → 対象外（理由メモ付き）。
- ハーネス（A）の検出結果もここに流し込み、「外の世界の脆弱性」と「自分のコード・イメージの検出」を同じ一覧で見る。

### 画面（最小構成）
1. **ダッシュボード**：重要度順の未対応リスト、「今日の新規」だけを抜いたビュー。
2. **資産ページ**：製品ごとに、関係する CVE と状態、現在のバージョン。
3. **詳細**：CVE 番号、出典リンク、要約、自分の判断メモ、対応履歴。

### 置き場所と公開範囲
- Coolify 上に小さく立てる（Web アプリ＋SQLite 程度の軽さ）。公開はせず、Cloudflare Access の内側だけに置く。
- 朝のダイジェスト（8:47 配信）は、このトラッカーの「今日の新規・要対応」から生成する形に寄せると、ニュースと対応状況がずれない。

### データの持ち方（報告書に直結させる）
報告書を後から手作業で書くのではなく、**日常の記録そのものが報告書の材料になる**ように、トラッカーの各項目に最初から次のフィールドを持たせる。
- **概要**：何の脆弱性・検出か（1〜3文）、重要度、状態、発見日・出典
- **範囲**：影響を受ける資産（製品・バージョン・台数/場所）、影響を受けないと確認できた範囲
- **対応方法**：実施する／した対応（パッチ適用、設定変更、緩和策、様子見の判断理由）、手順メモ、担当、期限、実施日
- 根拠：CVE 番号、出典リンク、ハーネスの検出出力への参照

## C. 報告書の生成

### 種類
1. **個別報告書**：1件の脆弱性／検出ごと。対応が完了した時点で「対応済み報告書」として確定できる。
2. **定期報告書**：週次・月次のまとめ。期間内の新規・対応中・完了・対象外を集計し、未対応の残件を先頭に出す。

### 章立て（テンプレート）
1. **概要**：対象の脆弱性／検出の要約、重要度、現在の状態、関係する日付（公表日・発見日・対応日）
2. **範囲**：影響を受ける資産の一覧と影響内容、影響を受けないと確認した資産、その確認方法
3. **検出内容と根拠**：CVE 番号・CVSS、出典リンク、ハーネスの検出結果（該当箇所・出力の抜粋）
4. **対応方法**：採用した対応とその手順、代替案を採らなかった理由、緩和策で済ませた場合はその内容と限界
5. **対応結果と残課題**：実施結果の確認方法（再スキャン等）、残っているリスク、次にやること
6. **参考**：出典・関連リンク一覧

### 生成のしかた
- トラッカーの項目データから章立てに沿って自動で組み立てる（概要・範囲・対応方法は上記フィールドからそのまま入る）。人の手は「判断メモ」と「残課題」の追記だけに寄せる。
- 出力は Markdown を正とし、必要に応じて PDF 化する。ファイル名は `report-YYYYMMDD-<連番またはCVE>.md`。
- ハーネス（A）の実行結果も同じ章立てに流し込めるように、ハーネス側のレポート JSON にも「概要・範囲・対応方法（推奨）」の欄を持たせる。

## 進め方（段階）
1. **Phase 1（トラッカーの読み取り専用版）**：KEV＋JPCERT＋OSV の取り込みと、インベントリ手動登録、一覧表示だけ。状態管理はまだ持たない。
2. **Phase 2（ハーネスの最小版）**：リポジトリ対象に OSV-Scanner＋gitleaks だけをサンドボックスで回し、結果 JSON を出す。
3. **Phase 3（統合）**：状態管理、ハーネス結果の取り込み、朝ダイジェストの生成元をトラッカーに切り替え、報告書（個別・定期）の自動生成を有効化。
